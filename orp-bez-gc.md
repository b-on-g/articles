# Говорят «Реактивность не бесплатна»

Rust и Zig хвалят за компактность в памяти, zig особенно в wasm. 

> нам нужен новый реактивный яп без GC

Ответ прилетает через минуту:

> Берёшь любую либу для реактивности и пользуешь. Реактивность не бесплатна.

Вот на этой фразе я и завис. Её говорят всегда с таким видом, будто остальное бесплатно. При этом у того же собеседника в любимом языке либо счётчик ссылок, который трогает память на каждом копировании указателя, либо сборщик, который время от времени останавливает мир. За это тоже платят, просто платёж давно стал фоном и его перестали замечать.

Скажу сразу, о чём текст. Реактивный граф, если он устроен правильно, уже знает про программу всё, что сборщику мусора приходится выяснять обходом кучи. Он знает, кто кого читает и когда значение перестало быть кому-то нужным. Мне кажется странным, что эту информацию собирают дважды: один раз для пересчёта, второй раз для уборки.

### Что я называю реактивностью

Не потоки и не подписки. Rx и его клоны в каждом языке проталкивают изменения от источника к потребителю, и программист сам решает, на что подписаться и когда отписаться. Забыл отписаться, получил утечку. Подписался дважды, получил двойной пересчёт. Поэтому в чате я и назвал эту реактивность кривой.

Есть второй способ, его Карловский в 2017 году назвал Объектным Реактивным Программированием. Вычисление начинается от потребителя. Метод при вызове запоминает, к чему обращался, кеширует результат и сбрасывает кеш, когда что-то из прочитанного поменялось. В моле это выглядит как обычный класс:

```ts
class User {
	@ $mol_wire_solo age( next = 0 ) { return next }
	@ $mol_wire_solo adult() { return this.age() >= 18 }
}
```

`adult` не подписывается на `age` руками. Он просто его прочитал, и граф это записал. Поменяли возраст, и `adult` пересчитается, но только если его кто-то спросит.

Самая массовая реактивная программа в мире так и работает, это электронная таблица. Ячейка с формулой не знает, что она «подписчик». Бухгалтеры пользуются ОРП сорок лет и не жалуются, что это сложно.

### При чём тут Smalltalk

Smalltalk-80 из Xerox PARC дал нам почти всё, чем мы пользуемся: всё объект, посылка сообщений, позднее связывание, живая система, которую правишь на ходу. Кэй отдельно настаивал, что главное там сообщения, а не классы.

Одного там не было. Актуальность состояния поддерживал программист: сам решал, когда что пересчитать, сам рассылал уведомления об изменениях. MVC Реенскауга родился ровно там и ровно ради этого, чтобы вид узнавал, что модель поменялась.

Позднее связывание у Кэя означает, что кто ответит на сообщение, решается в момент обращения. Pull-реактивность означает, что значение тоже вычисляется в момент обращения. Это одна идея, применённая к двум вещам: к поиску метода и к самому состоянию. В моле её довели до конца, поэтому я и говорю про него «Smalltalk плюс спредшит».

Про Smalltalk у меня отдельно лежит большой материал, тут только та часть, которая нужна для дальнейшего.

### Почему этого нет на бэке

Бэкенд живёт запросом. Пришёл, посчитал, отдал, забыл. Всё, что должно пережить запрос, уезжает в кеш, а кеш инвалидируется руками: TTL на глазок, ключи с версиями, удаление по событию из очереди. В README `$mol_wire` есть фраза про то, что он решает первую из двух сложных проблем информатики. Там это шутка, но инвалидация кеша действительно перестаёт быть проблемой, когда зависимости записаны в графе, а не в голове у разработчика.

Сервер, у которого состояние долгоживущее, это ровно тот случай, где граф окупается: соединения, подписки клиентов, производные данные, которые сейчас пересчитываются кроном. Только писать это приходится библиотекой поверх языка, и язык про граф ничего не знает.

### Почему этого нет в языках

Когда реактивность живёт в библиотеке, компилятор её не видит. Он не может проверить, что тело вычисления чистое, не может сказать, что метод делает ввод-вывод, не может выкинуть то, что никто не читает.

Тот же собеседник в чате правильно заметил про Rust: по сигнатуре функции не понять, выделяет ли она память в куче и ходит ли в сеть, а это самые дорогие операции. Добавь сверху макросы, трейты и перегрузки, и скрытой сложности становится больше, чем явной.

В реактивном языке это знание лежит в самой модели. Чистое вычисление, состояние и действие с эффектами объявляются разными словами, и проверять их различие может компилятор, а не код-ревью.

### Граф уже знает, когда убирать

Теперь про главное. Посмотрим, как мол освобождает ресурсы, это несколько строк в `mol/wire`.

Издатель хранит своих подписчиков. Когда отписывается последний, вызывается `reap()`:

```ts
sub_off( sub_pos: number ) {
	// …
	if( end === this.sub_from ) this.reap()
}
```

Волокно в `reap()` не умирает сразу, а встаёт в очередь. В конце такта планировщик проходит очередь, и у кого подписчики так и не появились, получает деструктор. В коде этот цикл прямо подписан «Collect garbage»:

```ts
// Collect garbage
while( this.reaping.size ) {
	const fibers = this.reaping
	this.reaping = new Set
	for( const fiber of fibers ) {
		if( !fiber.sub_empty ) continue
		fiber.destructor()
	}
}
```

Второй механизм отвечает за владение. Если атом сам создал объект, он им владеет. Когда атом получает новое значение, старое разрушается сразу:

```ts
if( $mol_owning_check( this, prev ) ) {
	prev.destructor()
}
```

Что должно жить всегда, помечается `$mol_wire_solid()`. Это отключает уборку для конкретного узла, явно и в одном месте.

Получается, момент смерти объекта предсказуем: значение заменили, или до конца такта у узла не нашлось читателя. В README так и написано: «we don't rely on garbage collector». Сокеты, таймеры, DOM-узлы закрываются, когда перестали быть нужны, а не когда сборщику захотелось пройтись по куче.

Сравни, что делают альтернативы:

  * **Трассирующий сборщик** обходит граф объектов, чтобы выяснить, что достижимо. Этот граф у реактивной программы уже построен и поддерживается.
  * **Счётчик ссылок** платит инкрементом и декрементом на каждом копировании указателя и течёт на циклах, поэтому к нему прикручивают слабые ссылки или тот же сборщик циклов.
  * **Реактивный граф** уже заплатил за учёт зависимостей ради пересчёта. Время жизни достаётся следствием той же бухгалтерии.

Важная оговорка: мол работает в JS, и куча там всё равно под сборщиком. Без GC он обходится в том смысле, что не полагается на него в вопросе, когда закрыть ресурс. Проверить, держится ли идея целиком, без сборщика под ногами, можно только своим языком.

### Поэтому я делаю свой язык

Называется wire. Правила жёсткие: только реактивные методы, никаких переменных и стрелочных функций. Состояние, как в моле, объявляется параметром `next?`, действия отдельным словом `action`, корни, которые должны пережить такт, словом `solid`. Компилятор написан на TS, генерирует C, собирается `zig cc`.

Кусок примера с магазином:

```
object $bog_wire_shop {

	solid catalog = $bog_wire_shop_catalog()
	solid cart = $bog_wire_shop_cart()

	line( sku: text ) = $bog_wire_shop_line {
		sku <= sku
		cart <= cart
	}

}
```

Строка корзины создаётся методом `line( sku )`, принадлежит графу и умирает, когда её больше никто не читает. Объекты живут по графу. Значения неизменяемые и считаются счётчиком ссылок, но из неизменяемых значений цикл не собрать, поэтому счётчик тут не течёт.

После каждого теста рантайм проверяет, что в нём осталось ноль узлов и ноль значений. Чтобы убедиться, что проверка не врёт, я специально вбрасывал утечку, и тест краснел.

### Так бесплатна или нет

Нет, конечно. Каждый мемоизированный метод это узел в графе, у узла есть список издателей и подписчиков, это память и такты. Только сравнивать надо не с нулём, а с тем, что ты платишь иначе: со сборщиком, со счётчиком ссылок, с ручными отписками и с кешем, который инвалидируешь по TTL и надеешься на лучшее.

В чате мне ответили, что всё это уже где-то есть, нужно только допилить до некринжовой версии. Я ответил, что в моле допилено. Меня назвали сектантом.
