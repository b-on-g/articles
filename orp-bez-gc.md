# Говорят «Реактивность не бесплатна»

Rust и Zig хвалят за компактность по памяти, Zig особенно в wasm.

Rust экономит на сборщике мусора, но платит владением и счётчиками ссылок там, где владение не выразить. Zig вообще отдаёт память программисту: держи аллокатор и не забудь освободить. Остальные живут с GC и платят за него памятью под кучу, барьерами и паузами.

Стоит предложить встроить в язык реактивность, и звучит одно и то же: реактивность не бесплатна, бери библиотеку. Говорят это так, будто всё остальное бесплатно. Платёж за сборщик и за счётчики давно стал фоном, его просто перестали замечать.

Мой тезис такой. Реактивный граф, если он устроен правильно, уже знает про программу то, что сборщику приходится выяснять обходом кучи: кто кого читает и когда значение перестало быть кому-то нужным. Программа собирает эти связи ради пересчёта, а потом GC второй раз обходит те же связи ради уборки.

В конце покажу язык, где после каждого теста рантайм проверяет, что в памяти ноль узлов и ноль значений, и объясню, почему для этого пришлось запретить переменные. Но начнём с бага, который писал каждый.

### Утечка, которую писал каждый

Компонент чата, Angular, RxJS:

```ts
ngOnInit() {
	webSocket( this.url ).subscribe( message => this.last = message )
}
```

Ушли со страницы, компонент уничтожен, сокет открыт. Подписка держит замыкание, замыкание держит компонент, и сборщик мусора ничего с этим не сделает: с его точки зрения всё достижимо. Лечится `takeUntil( this.destroy$ )`, `async`-пайпом или ручным `unsubscribe` в `ngOnDestroy`. То есть программист руками дублирует знание, которое у фреймворка и так есть: компонент больше никому не нужен.

Rx проталкивает изменения от источника к потребителю, и кто на что подписан, решает программист. Когда советуют «взять любую либу для реактивности», обычно имеют в виду её.

Тот же чат на $mol:

```ts
class $my_chat extends $mol_object2 {
	@$mol_mem
	socket() {
		const socket = new WebSocket(this.url())
		socket.onmessage = event => this.last(event.data)
		return Object.assign(socket, { destructor: () => socket.close() })
	}

	@$mol_mem
	last(next = '') {
		this.socket()
		return next
	}
}
```

Отписки нет, потому что подписки руками тоже нет. `last` прочитал `socket`, граф это записал. Пока `last` кто-то показывает, сокет жив. Компонент ушёл с экрана, у `last` не осталось подписчиков, у `socket` тоже, и в конце тика атом с сокетом уничтожается, а вместе с ним вызывается `destructor`, который закрывает соединение.

Эту парадигму Дмитрий Карловский в 2017 году назвал Объектно Реактивным Программированием. Вычисление начинается от потребителя: метод при вызове запоминает, к чему обращался, кеширует результат и сбрасывает кеш, когда прочитанное поменялось.

### Excel, самый популярный ЯП в мире

Звучит как шутка, но формулы в Excel это программа, причём чисто функциональная, а с появлением `LAMBDA` ещё и полная по Тьюрингу. Пишут на этом языке бухгалтеры, логисты и финансисты, которые слова «реактивность» не слышали.

Устроен он ровно как ОРП. Excel строит дерево зависимостей между ячейками. Поменяли ячейку, и всё, что от неё зависит, помечается «грязным». Пересчитываются только грязные ячейки, остальные отдают закешированное значение. Никто не подписывается на `A1` и никто не отписывается, ссылка в тексте формулы и есть подписка.

Посмотрите, чего в Excel нет. Нет сборщика мусора для формул. Стёрли формулу в `C3`, и её зависимости исчезли вместе с ней. Удалили лист, и пересчитывать стало нечего. Время жизни вычисления там равно времени жизни ячейки, а её видно глазами. Сорок с лишним лет, начиная с VisiCalc 1979 года, эта модель работает у сотен миллионов людей без единой утечки подписки.

Разница с молом одна, но важная. Excel в автоматическом режиме пересчитывает все грязные ячейки сразу, даже те, которых никто не видит. Мол пересчитывает только то, что прочитали. Компонент за пределами экрана никто не спрашивает, поэтому он не вычисляется вообще.

Программисты при этом пишут `takeUntil( this.destroy$ )` и спорят, бесплатна ли реактивность.

Реактивная таблица, кстати, первое, что я собрал на своём языке, о котором ниже:

```sh
printf 'PRICE = 120\nQTY = 3\nTOTAL = PRICE * QTY\nQTY = 4\n' | bog/wire/demonative/-/native
```

```
PRICE = 120
QTY = 4
TOTAL = 480
```

Поменяли `QTY`, пересчитался `TOTAL`, и больше ничего.

### Откуда ноги растут

ОРП продолжает идеи Smalltalk-80. Кэй настаивал, что главное в объектах сообщения и позднее связывание: кто ответит, решается в момент обращения. Одного в Smalltalk не было, актуальность состояния поддерживал программист, и MVC Реенскауга появился там как раз ради ручной рассылки «модель поменялась».

Pull-реактивность применяет то же позднее связывание к значению: сколько это равно, тоже решается в момент обращения. Поэтому я называю мол «Smalltalk плюс спредшит».

### Почему сборщик тут не помощник

Тут обычно возражают, что в современных GC паузы stop-the-world почти незаметны. У Go они меньше миллисекунды, у ZGC и Shenandoah тоже. Это правда, только паузы тут ни при чём.

Сборщик убирает память и ничего не знает про сокеты, файлы, таймеры и подписки. В Java для этого был `finalize()`, его признали ошибкой: метод вызывается когда-нибудь или никогда, и с Java 18 (JEP 421) финализация помечена к удалению. Вместо неё в языках со сборщиком появились `try-with-resources`, `using`, `defer`. То есть ресурсы во всех этих языках освобождают руками, просто мы привыкли.

Раскурим как это делает мол в нескольких строках `mol/wire`. Когда от атома отписывается последний подписчик, вызывается `reap()`, и атом попадает в очередь на уборку. В конце тика планировщик проходит очередь, и прямо в коде этот цикл подписан «Collect garbage»:

```ts
// Collect garbage
while (this.reaping.size) {
	const fibers = this.reaping
	this.reaping = new Set()
	for (const fiber of fibers) {
		if (!fiber.sub_empty) continue
		fiber.destructor()
	}
}
```

Второй механизм отвечает за владение. Атом владеет объектом, который сам создал, и при новом значении старое разрушается сразу:

```ts
if ($mol_owning_check(this, prev)) {
	prev.destructor()
}
```

Что должно жить всегда, помечается `$mol_wire_solid()`, явно и в одном месте. Момент смерти предсказуем: значение заменили, или до конца тика у атома не нашлось подписчика.

Оговорка: мол работает в JS, и память там всё равно убирает сборщик. Без GC мол обходится в том смысле, что не полагается на него, когда закрыть ресурс. Обойтись без сборщика целиком можно только в языке, где граф видит все ссылки. К этому вернусь ниже.

### Аутбокс и Кафка

Теперь бэкенд. Типовая задача: сервис заказов сохраняет заказ и сообщает остальным. Наивно пишут в базу и следом в Кафку. Между двумя записями сервис падает, и заказ есть, а события нет, или наоборот. Это dual write.

Стандартное решение --- transactional outbox. Событие пишут в таблицу `outbox` той же транзакцией, что и заказ. Отдельный процесс, поллер или Debezium через CDC, читает таблицу и шлёт в Кафку. Доставка at-least-once, поэтому каждый потребитель хранит id обработанных событий и выкидывает дубли. Из событий потребители собирают свои проекции: остатки на складе, баланс, витрину для поиска.

Посмотрите, что тут на самом деле происходит. Проекция у потребителя это производное значение от чужого состояния. Событие `OrderCreated` по сути говорит «твой кеш устарел, пересчитай». Таблица outbox играет роль очереди инвалидации, поллер рассылает уведомления, дедупликация чинит то, что уведомление может прийти дважды. Это реактивный граф, собранный руками из таблицы, демона, брокера и таблицы обработанных id, и устроен он по push-модели, со всеми болячками Rx из первого примера.

В pull-модели потребитель держит проекцию как функцию от состояния источника. По сети едет состояние с версией, а не команда «что-то поменялось». Повторно пришедшая та же версия ничего не меняет, потому что атом сравнивает новое значение со старым и при равенстве никого не будит. Дедупликация получается сама. Синк в Гипер Базе устроен по этому принципу: узлы обмениваются состоянием, а не событиями.

Вот как это выглядит на wire, языке, про который речь пойдёт ниже. Заказы и склад, без таблицы outbox, без событий и без поллера:

```typescript
type $bog_wire_outbox_order {
	id: text
	sku: text
	qty: int
}

object $bog_wire_outbox_orders {

	solid all( next?: list $bog_wire_outbox_order ) = next ?? []

	id_of( order: $bog_wire_outbox_order ) = order.id

	action place( id: text, sku: text, qty: int ) {
		all( all.upsert( id_of, id, $bog_wire_outbox_order{ id, sku, qty } ) )
	}

	action cancel( id: text ) {
		all( all.drop( id_of, id ) )
	}

}

object $bog_wire_outbox_reserve {

	sku: text
	orders: $bog_wire_outbox_orders

	taken( order: $bog_wire_outbox_order ) = order.sku == sku ? order.qty : 0

	qty = orders.all.map( taken ).sum

}

object $bog_wire_outbox_stock {

	orders: $bog_wire_outbox_orders

	solid total( sku: text, next?: int ) = next ?? 0

	reserve( sku: text ) = $bog_wire_outbox_reserve {
		sku <= sku
		orders <= orders
	}

	free( sku: text ) = total( sku ) - reserve( sku ).qty

}
```

Сервис заказов только пишет свои заказы. Склад ничего не слушает: `free( sku )` это проекция, она читает заказы и пересчитывается, когда они поменялись. Резерв по товару создаётся объектом, пока его кто-то спрашивает, и уничтожается, когда перестали.

Тесты на те три вещи, ради которых обычно городят outbox:

```typescript
action order_reserves_stock() {
	stock.total( "tea", 10 )
	orders.place( "o1", "tea", 3 )
	orders.place( "o2", "tea", 2 )
	assert( stock.free( "tea" ) == 5 )
}

action same_order_twice_counts_once() {
	stock.total( "tea", 10 )
	orders.place( "o1", "tea", 3 )
	orders.place( "o1", "tea", 3 )
	assert( stock.free( "tea" ) == 7 )
}

action cancel_returns_stock() {
	stock.total( "tea", 10 )
	orders.place( "o1", "tea", 3 )
	orders.cancel( "o1" )
	assert( stock.free( "tea" ) == 10 )
}
```

```
ok $bog_wire_outbox_test.order_reserves_stock
ok $bog_wire_outbox_test.same_order_twice_counts_once
ok $bog_wire_outbox_test.cancel_returns_stock
```

Повторный заказ `o1` не задвоил резерв, потому что `upsert` по id записал то же самое, и дедупликация не понадобилась. Отмена вернула товар на склад, и компенсирующее событие тоже не понадобилось. После каждого теста рантайм ещё и проверил, что ни один объект резерва не остался висеть в памяти.

Граница тоже есть. Граф не делает базу и брокер атомарными, если вам нужны две системы, транспорт с гарантией доставки понадобится всё равно. Меняется то, что по нему едет, и количество кода вокруг: проекции, ретраи и дедупликация перестают быть ручными.

### Erlang ближе всех

Если искать среди живых языков то, где время жизни ресурса привязано к модели, лучше всего подходит Erlang.

У каждого процесса своя куча и свой сборщик, поэтому общего stop-the-world нет, каждый процесс чистит только свою маленькую кучу. Процесс владеет ресурсами: умер процесс, и закрылись его порты, удалились ETS-таблицы, которыми он владел, а связанные процессы получили сигнал. Супервизоры выстраивают дерево владения, очень похожее на владение атомами в моле.

Отличия принципиальные:

- Erlang шлёт сообщения, то есть это push. Производное состояние согласует программист: процесс сам решает, кому разослать обновление, получатели сами держат кеши.
- Процесс живёт, пока его не убили или он не завершился. Нужен ли он ещё кому-то, рантайм не знает. В моле атом умирает именно потому, что у него не осталось подписчиков.
- Внутри процесса всё равно работает сборщик.

Erlang решил вопрос, кто владеет ресурсом. Вопрос, нужен ли он ещё кому-то, остался на программисте.

### Почему этого нет в языках

Пока реактивность живёт в библиотеке, компилятор её не видит. Он не может проверить, что тело вычисления чистое, не может сказать, что метод делает ввод-вывод, не может выкинуть то, что никто не читает.

У Rust с этим отдельная история: по сигнатуре функции не понять, выделяет ли она память в куче и ходит ли в сеть, а это самые дорогие операции. Макросы, трейты и перегрузки добавляют скрытой сложности сверху.

Главное препятствие в другом. Граф может заменить сборщик, только если видит все ссылки. В JS объект можно положить в переменную, в массив, в замыкание, и граф про эту ссылку не узнает. Тогда «у атома нет подписчиков» уже не значит «объект никому не нужен».

### wire

Поэтому я сделал язык, где граф видит всё: [wire](https://github.com/b-on-g/wire). Правила такие:

- только методы, переменных нет;
- лямбд нет, в `map`, `find`, `upsert`, `drop` передаются именованные методы;
- состояние объявляется параметром `next?`, как в моле, писать в него можно только из `action`;
- тела мемо чистые, это проверяет компилятор;
- что должно пережить тик без подписчиков, помечается `solid`.

Запрет переменных и лямбд тут не вкусовщина. Без них ссылка на объект может лежать только в результате атома, и граф знает о каждой.

Строка корзины из примера магазина:

```typescript
object $bog_wire_shop_line {

	sku: text
	cart: $bog_wire_shop_cart
	catalog: $bog_wire_shop_catalog

	qty = cart.qty( sku )

	sum = catalog.price( sku ) * qty

	label = "{sku} x{qty} = {sum}"

}
```

Магазин создаёт строки из корзины:

```typescript
line( sku: text ) = $bog_wire_shop_line {
	sku <= sku
	cart <= cart
	catalog <= catalog
}

lines = cart.skus.map( line )

total = lines.map( line_sum ).sum
```

Удалили товар из корзины, `lines` пересчитался, строки с этим товаром больше никто не читает, и в конце тика она уничтожена. Объектами владеет граф: объект принадлежит первому атому, который его вернул, и умирает вместе с ним. Значения неизменяемые и считаются счётчиком ссылок. Из неизменяемых значений цикл не собрать, поэтому счётчик тут не течёт.

### Как это выглядит на C

Компилятор написан на TS, генерирует C и собирает его `zig cc`. Каждый метод превращается в обычную функцию пересчёта. Вот `sum` из примера выше:

```c
static void F_bog_wire_shop_line__sum( wire_obj* self, const wire_val* keys, const wire_val* next, wire_val* out ) {
	wire_val t165 = wire_read( self, &M_bog_wire_shop_line__catalog, NULL, NULL );
	wire_val t166 = wire_read( self, &M_bog_wire_shop_line__sku, NULL, NULL );
	wire_val t167[] = { t166 };
	wire_val t164 = wire_read( t165.obj, &M_bog_wire_shop_catalog__price, t167, NULL );
	wire_val t168 = wire_read( self, &M_bog_wire_shop_line__qty, NULL, NULL );
	wire_val t163 = { .i = t164.i * t168.i };
	*out = t163;
}
```

Вся реактивность сидит в `wire_read`. Он отдаёт закешированное значение или пересчитывает его и записывает, что текущий атом прочитал этот. Так можно писать и руками, без моего языка: описал член структурой `wire_member` с функцией пересчёта, читаешь через `wire_read`, рантайм из `rt/rt.h` делает остальное. Язык нужен, чтобы компилятор не дал положить ссылку мимо графа.

А вот весь «сборщик мусора» рантайма:

```c
static void reap( void ) {
	while( rt.touched.len || rt.orphans.len ) {
		wire_ids touched = ids_take( &rt.touched );
		for( int i = 0; i < touched.len; ++i ) evict( touched.items[ i ] );
		ids_free( &touched );

		wire_ids orphans = ids_take( &rt.orphans );
		for( int i = 0; i < orphans.len; ++i ) {
			wire_node* node = get( orphans.items[ i ] );
			if( node && !node->has_owner && !node->root ) destroy( orphans.items[ i ] );
		}
		ids_free( &orphans );
	}
}
```

Обхода кучи нет. Рантайм разбирает только те узлы, которых коснулись за тик: у кого пропали подписчики и у кого пропал владелец.

После каждого теста рантайм сверяет число живых узлов и значений с тем, что было до теста, и при расхождении печатает `leaked N values, M nodes` и роняет сборку. Чтобы убедиться, что проверка не врёт, я специально вбрасывал утечку, и тест краснел. Та же проверка стоит на выходе из `main`.

Пример магазина в нативной сборке весит 78 904 байта, пиковый RSS 1,5 МБ на macOS, вместе с рантаймом. [TODO: те же цифры для такой же корзины на Rust, Go и Node.js, иначе сравнивать не с чем]

### Так бесплатна или нет

Нет, конечно. Каждый мемоизированный метод это узел графа со списками зависимостей и подписчиков, это память и процессорное время. Только сравнивать надо не с нулём. Сравнивать надо со сборщиком, со счётчиками ссылок, с `takeUntil` в каждом компоненте, с таблицей outbox, поллером и дедупликацией у каждого потребителя.

Реактивность не бесплатна. Просто за неё уже заплачено, когда граф строили ради пересчёта, и платить второй раз за уборку незачем.

Код, тесты и пример таблицы в терминале лежат в [репозитории wire](https://github.com/b-on-g/wire).

### Что дальше

Свой язык это чистый эксперимент. Интереснее другое: что будет, если тот же граф принести в языки, на которых уже пишут бэкенд.

**Rust.** Владение там есть в самом языке, и кажется, что граф ему не нужен. На деле `Rc<RefCell<…>>` в любом UI или игровом движке на Rust это ручной граф, который течёт на циклах. У меня уже работает реактивный рантайм на Rust с владением как в моле: арена с поколениями, атом владеет значением, уборка без счётчиков ссылок. Он лежит в [PR в mam_mol](https://github.com/hyoo-ru/mam_mol/pull/926), а [демо](https://b-on-g.github.io/rsdemo/) крутится в браузере через wasm. Про то, где владение Rust помогает графу, а где мешает, будет отдельная статья.

**Go.** Сборщик там есть, а ресурсы всё равно закрывают через `defer` и `context.Cancel`. Вопрос, который я хочу проверить: сможет ли граф отменять горутины и закрывать соединения сам, когда результат перестал быть кому-то нужен, и сколько `ctx` после этого останется в коде.

**C и C++.** Рантайм wire уже на C, и писать против него можно руками. В C++ есть RAII, то есть деструктор вызывается в предсказуемый момент. Не хватает только ответа на вопрос, когда этот момент наступает для объекта, который делят несколько потребителей. Граф как раз отвечает на этот вопрос, и `shared_ptr` тут ему не нужен.

Если хочется посмотреть на какой-то из этих языков раньше, напишите в комментариях, с какого начать.
