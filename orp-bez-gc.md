# Говорят «Реактивность не бесплатна»

Rust и Zig хвалят за компактность по памяти, Zig особенно в wasm.

Rust экономит на сборщике мусора, но платит владением и счётчиками ссылок там, где владение не выразить. Zig вообще отдаёт память программисту: держи аллокатор и не забудь освободить. Остальные живут с GC и платят за него памятью под кучу, барьерами и паузами.

Стоит предложить встроить в язык реактивность, и звучит одно и то же: реактивность не бесплатна, бери библиотеку. Как будто сборщик бесплатный)

А ведь реактивный граф уже знает, кто кого читает и когда значение стало никому не нужно. Сборщик выясняет то же самое, только обходом кучи. Получается, одну и ту же информацию мы собираем дважды.

### Excel, самый популярный ЯП в мире

Формулы в Excel это программа, чисто функциональная, а с `LAMBDA` ещё и полная по Тьюрингу. Excel строит дерево зависимостей между ячейками, поменяли ячейку, и всё зависящее помечается грязным и пересчитывается. Никто не подписывается на `A1` и никто от неё не отписывается, ссылка в формуле и есть подписка. Стёрли формулу, и её зависимости исчезли вместе с ней. Сборщика мусора для формул там нет и никогда не было.

Бухгалтеры так живут с 1979 года, со времён VisiCalc. А мы пишем `takeUntil( this.destroy$ )` в каждом компоненте.

Отличие от мола одно: Excel пересчитывает все грязные ячейки, даже те, что за экраном. В моле считается только то, что прочитали.

Реактивную таблицу я, кстати, первым делом собрал на своём языке, про него ниже:

```sh
printf 'PRICE = 120\nQTY = 3\nTOTAL = PRICE * QTY\nQTY = 4\n' | bog/wire/demonative/-/native
```

```
PRICE = 120
QTY = 4
TOTAL = 480
```

### Откуда ноги растут

У Кэя в Smalltalk главное это сообщения и позднее связывание: кто ответит, решается в момент обращения. А вот актуальность состояния там поддерживал программист руками, MVC ровно для этого и придумали. Pull-реактивность доводит позднее связывание до значения: сколько это равно, тоже решается в момент обращения. Поэтому мол для меня это Smalltalk плюс спредшит.

Дмитрий Карловский в 2017 году назвал это Объектно Реактивным Программированием. Метод при вызове запоминает, что прочитал, кеширует результат и сбрасывает кеш, когда прочитанное поменялось. Вот чат на моле:

```ts
class $my_chat extends $mol_object2 {

	@ $mol_mem
	socket() {
		const socket = new WebSocket( this.url() )
		socket.onmessage = event => this.last( event.data )
		return Object.assign( socket, { destructor: ()=> socket.close() } )
	}

	@ $mol_mem
	last( next = '' ) {
		this.socket()
		return next
	}

}
```

Пока `last` кто-то показывает, сокет жив. Компонент ушёл с экрана, подписчиков у `last` не осталось, у `socket` тоже, и в конце тика атом уничтожается вместе с сокетом. Отписываться не от чего, руками ни на что не подписывались.

Раскурим, как это сделано в `mol/wire`. Когда от атома отписывается последний подписчик, он попадает в очередь, и в конце тика планировщик её разбирает. Цикл в коде так и подписан:

```ts
// Collect garbage
while( this.reaping.size ) {
	const fibers = this.reaping
	this.reaping = new Set
	for( const fiber of fibers ) {
		if( !fiber.sub_empty ) continue
		fiber.destructor()
	}
}
```

Плюс владение: атом владеет объектом, который сам вернул, и при новом значении старое уничтожается сразу. Что должно жить всегда, помечается `$mol_wire_solid()`.

### Где у меня текло

Звучит красиво, но я за последние пару месяцев наловил утечек в своём же коде на моле. Все разные, а механизм один.

Таймер в меме. Завёл `$mol_after_timeout` в теле мема перед асинхронным вызовом. Тело при ожидании промиса прогоняется дважды: первый раз бросает промис, второй раз дорабатывает с результатом. Каждый прогон заводил свой таймер, а таймер через секунду снова дёргал мем. Таймеров каждую секунду становилось вдвое больше, куча доросла до 1,8 ГБ при 96% CPU. Таймер жил сам по себе, граф про него ничего не знал.

`solid` на атоме, который читает глобальный кэш. `solid` выключает уборку навсегда, атом никогда не отписывается от источников, а источник глобальный и живёт вечно. Объект выпал из всех списков, но висел в памяти, и узел на сервере восемь раз падал по OOM на 3,6 ГБ. Лечится тем, что `solid` держит атом только пока жив его хозяин.

Сокет без деструктора на промисе. Атом с подключением сменил значение, пока сокет ещё был в `CONNECTING`. Промис деструктора не имел, и брошенный сокет потом спокойно открывался и жил вечно с пингами. Первый фикс глушил только `onclose`, а `close()` в `CONNECTING` по спецификации сначала стреляет `error`, и `onerror` ставил реконнект: 7 сокетов за 5,5 секунды. Деструктор над сокетом должен снимать все четыре обработчика.

GL-буфер без мема. Метод, который отдаёт параметры шейдера, был без мемоизации, каждый вызов создавал новый объект, а у объекта свой `createBuffer()`. Новый буфер каждый кадр, и видеопамять течёт, пока драйвер терпит.

Бывает и наоборот. В тесте записал данные в задаче, а потом прочитал пустоту. Атом был подписан только на эту задачу, задача закончилась, подписчиков не осталось, и граф честно убрал объект. В приложении такого нет, там его держит рендер.

Во всех случаях ресурс шёл мимо графа: таймер вне владения, `solid` без хозяина, промис без деструктора, объект вне мема. Там, где граф всё видел, всё убиралось само и вовремя.

### Почему сборщик тут не поможет

Тут обычно возражают, что в современных GC паузы stop-the-world почти незаметны. У Go они меньше миллисекунды, у ZGC и Shenandoah тоже. Это правда, но ни одну утечку выше сборщик бы не поймал: таймер, сокет и GL-буфер с его точки зрения достижимы.

Сборщик убирает память и ничего не знает про сокеты, файлы и таймеры. В Java для этого был `finalize()`, его признали ошибкой, и с Java 18 (JEP 421) финализацию собираются удалить. Поэтому в языках со сборщиком ресурсы закрывают руками: `try-with-resources`, `using`, `defer`.

Ближе всех к нормальному решению Erlang. Процесс владеет своими портами и ETS-таблицами, умер процесс, и всё его закрылось, а куча у каждого процесса своя, поэтому общего stop-the-world нет. Только процесс живёт, пока его не убили, нужен ли он ещё кому-то, рантайм не знает. И модель там push, кому разослать обновление, решает программист.

### Аутбокс и Кафка

На бэке тот же граф собирают руками и называют паттерном. Сервис заказов пишет заказ в базу и событие в Кафку, между двумя записями падает, это dual write. Лечат transactional outbox: событие кладут в таблицу той же транзакцией, Debezium или поллер шлёт его в Кафку, доставка at-least-once, поэтому каждый потребитель хранит id обработанных и выкидывает дубли. Из событий потребитель собирает свою проекцию, например остатки на складе.

Проекция это производное значение от чужого состояния, а `OrderCreated` по сути «твой кеш протух». Таблица outbox работает очередью инвалидации, поллер рассылает уведомления, дедупликация чинит повторы. Push-реактивность из таблицы, демона и брокера.

На wire склад просто читает заказы:

```typescript
object $bog_wire_outbox_reserve {

	sku: text
	orders: $bog_wire_outbox_orders

	taken( order: $bog_wire_outbox_order ) = order.sku == sku ? order.qty : 0

	qty = orders.all.map( taken ).sum

}

object $bog_wire_outbox_stock {

	orders: $bog_wire_outbox_orders

	solid total( sku: text, next?: int ) = next ?? 0

	reserve( sku: text ) = $bog_wire_outbox_reserve {
		sku <= sku
		orders <= orders
	}

	free( sku: text ) = total( sku ) - reserve( sku ).qty

}
```

Заказы это список с `upsert` по id, поэтому повторный заказ ничего не задваивает:

```typescript
action same_order_twice_counts_once() {
	stock.total( "tea", 10 )
	orders.place( "o1", "tea", 3 )
	orders.place( "o1", "tea", 3 )
	assert( stock.free( "tea" ) == 7 )
}
```

Отмена возвращает товар без компенсирующего события, а объект резерва уничтожается, когда его перестают спрашивать. Две системы граф атомарными, конечно, не сделает, транспорт между ними нужен всё равно. Но по нему можно гнать состояние с версией, а не события, так синкается Гипер База.

### wire

Все утечки выше были про то, что ресурс можно положить мимо графа. Так появился [wire](https://github.com/b-on-g/wire), язык, где мимо графа положить нельзя:

  * переменных нет, лямбд нет, в `map`, `find`, `upsert` передаются именованные методы;
  * состояние это параметр `next?`, писать в него можно только из `action`;
  * тела мемо чистые, это проверяет компилятор;
  * `solid` это модификатор метода, а не вызов где-то в теле.

Ссылка на объект может лежать только в результате атома, значит граф видит каждую. Объект принадлежит первому атому, который его вернул, и умирает вместе с ним. Значения неизменяемые и считаются счётчиком ссылок, цикл из неизменяемых значений не собрать, так что он не течёт.

Компилятор на TS, генерирует C и собирает его `zig cc`. Каждый метод становится обычной функцией, вся реактивность сидит в `wire_read`:

```c
static void F_bog_wire_shop_line__sum( wire_obj* self, const wire_val* keys, const wire_val* next, wire_val* out ) {
	wire_val t165 = wire_read( self, &M_bog_wire_shop_line__catalog, NULL, NULL );
	wire_val t166 = wire_read( self, &M_bog_wire_shop_line__sku, NULL, NULL );
	wire_val t167[] = { t166 };
	wire_val t164 = wire_read( t165.obj, &M_bog_wire_shop_catalog__price, t167, NULL );
	wire_val t168 = wire_read( self, &M_bog_wire_shop_line__qty, NULL, NULL );
	wire_val t163 = { .i = t164.i * t168.i };
	*out = t163;
}
```

Это `sum = catalog.price( sku ) * qty`. Так можно писать и руками на C против `rt/rt.h`, язык нужен только чтобы компилятор не дал завести таймер мимо графа)

Весь «сборщик мусора» рантайма:

```c
static void reap( void ) {
	while( rt.touched.len || rt.orphans.len ) {
		wire_ids touched = ids_take( &rt.touched );
		for( int i = 0; i < touched.len; ++i ) evict( touched.items[ i ] );
		ids_free( &touched );

		wire_ids orphans = ids_take( &rt.orphans );
		for( int i = 0; i < orphans.len; ++i ) {
			wire_node* node = get( orphans.items[ i ] );
			if( node && !node->has_owner && !node->root ) destroy( orphans.items[ i ] );
		}
		ids_free( &orphans );
	}
}
```

Кучу никто не обходит, разбираются только узлы, которых коснулись за тик.

После каждого теста рантайм сверяет число живых узлов и значений с тем, что было до теста, и при расхождении валит сборку с `leaked N values, M nodes`. Проверку я проверял, вбрасывал утечку, тест краснел. Пример магазина в нативной сборке весит 78 904 байта, пиковый RSS 1,5 МБ на macOS.

### Так бесплатна или нет?

Нет, каждый мем это узел со списками зависимостей и подписчиков. Только сравнивать надо со сборщиком, с `defer` и `takeUntil` по всему коду и с outbox у каждого сервиса, а не с нулём.
