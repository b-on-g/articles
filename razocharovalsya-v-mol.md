<details>
<summary>Шпаргалка по спецсимволам view.tree</summary>

- `-` комментарий, в код не попадает
- `$` префикс имени компонента, например `$mol_button`
- `/` массив, можно указать тип элементов: `sub /number`
- `*` словарь, ключи строки, значения любые
- `^` значение того же свойства у родителя, то есть `super`
- `\` сырая строка: `message \Привет`
- `@` локализуемая строка: `message @ \Привет`
- `<=` свойство владельца отдаётся вложенному компоненту, только чтение
- `=>` свойство вложенного компонента отдаётся владельцу, только чтение
- `<=>` свойство вложенного компонента целиком заменяется свойством владельца, двусторонняя связь
- `*` после имени свойства: свойство принимает ключ первым аргументом, `Task_row* $mol_view`
- `?` после имени свойства: значение можно записать, передав аргумент, `value? <=> name? \`

Источник: [readme `$mol_view`, раздел All special chars](https://github.com/hyoo-ru/mam_mol/tree/master/view#all-special-chars).

</details>

## Каждое свойство это точка расширения

Синтаксис непривычный, вот и вся претензия. Когда выходил jsx были такие же предъявы. При этом забивают на то, какие проблемы решает view.tree.

View.tree даёт гибкое переопределение и встроенную композицию:

> **Каждое свойство в view.tree это точка расширения.** Не нужно пытаться всё разнести на мелкогранулярные компоненты, иногда это просто не нужно. Упрощаем себе жизнь, переиспользование и понимание кода

Из компонента выше компилятор делает обычный js-класс:

```javascript
class $my_details extends $mol_view {
	page(next) {
		if (next !== undefined) return next
		return 0
	}
	Pager() {
		const obj = new this.$.$mol_paginator()
		obj.value = next => this.page(next)
		return obj
	}
	sub() {
		return [this.Pager()]
	}
}
$mol_mem($my_details.prototype, 'page')
$mol_mem($my_details.prototype, 'Pager')
```

Все его методы переопределяются:

```tree
$my_app $mol_div
	divs /
		<= Details $my_details
			page? <=> current_page? 3
```

`page` от `$my_details` получает значение из `current_page` приложения.

Стрелки показывают направление реактивного потока: `<=` приходит от текущего компонента, `<=>` двусторонняя связь, `=>` наоборот.

В `$mol` переопределение свойства ничем не отличается от создания: `city \Питер` и заводит свойство, и подменяет. Поэтому вопрос только в том, где эта строка, у родителя или у ребенка.

Воот где собака зарыта, погнали ломать

## 20 оверрайдов: ломаем восемью способами

Что из этого ловится ? Во второй версии в примере базовые компоненты переделаны, наследники нет, `git diff v1 v2 --stat` показывает только `base` и `widget`. Вот что получилось, v1 слева, v2 справа: [b-on-g.github.io/fragile](https://b-on-g.github.io/fragile/).

### Ловит компилятор

**Владелец настраивает вложенный компонент.** Это архитектурно встроенная композиция, обычный способ собирать интерфейс в `$mol`:
плюс в том, что не нужно специально выделять и выносить компонент, если не хочется или "так правильно"

```tree
$bog_fragile_outer_page $mol_view
	sub /
		<= Weather $bog_fragile_outer_widget
			city \Питер
```

В v2 виджет переименовал `city` в `location`. Страницу не трогали. Сборка:

```
error TS2339: Property 'city' does not exist on type '$bog_fragile_outer_widget'.
```

Падает, потому что view.tree генерирует не только js, но и d.ts, а в нём на каждую такую привязку лежит проверка типа:

```ts
type $bog_fragile_outer_widget__city_bog_fragile_outer_page_1 = $mol_type_enforce<
	string,
	ReturnType<$bog_fragile_outer_widget['city']>
>
```

![Случай outer: v1 рендерит Питер, v2 не собирается](https://raw.githubusercontent.com/b-on-g/fragile/main/article/fragile-outer.png)

Двадцать привязок дадут двадцать ошибок компиляции, а не тихий развал. Если бы `city` поменял тип, а не имя, упало бы так же.

- `retype`: наследник задаёт `limit 5`, родитель сменил тип `limit` на строку. TS2416.
- `rename/ts`: наследник в `view.ts` пишет `override heading()`, родитель переименовал `heading`. TS4113.

![Случай retype: смена типа ловится компилятором](https://raw.githubusercontent.com/b-on-g/fragile/main/article/fragile-retype.png)

![Случай rename/ts: override ловит переименование](https://raw.githubusercontent.com/b-on-g/fragile/main/article/fragile-rename-ts.png)

### Ловит только тест

- `rename/tree`: то же переименование, но наследник задаёт `heading` во view.tree. Сборка зелёная, на экране «База» вместо «Наследник», падает тест наследника.

![Случай rename/tree: сборка зелёная, на экране База](https://raw.githubusercontent.com/b-on-g/fragile/main/article/fragile-rename-tree.png)

### Не ловит ничего

- `collide/child`: у наследника своё свойство `icon` под скрепку, родитель завёл `icon` под колокольчик в шапке. Скрепка молча встала в шапку родителя.
- `spread/plain`: наследник перечислил содержимое родителя руками, родитель добавил шапку. Шапка молча пропала.

И два соседа, которые при тех же изменениях не ломаются: `collide/named` (свойство названо `attach_icon`) и `spread/keep` (содержимое родителя взято через `^`).

![Случаи collide и named: скрепка в шапке против колокольчика](https://raw.githubusercontent.com/b-on-g/fragile/main/article/fragile-collide.png)

![Случаи plain и keep: шапка пропала против шапка на месте](https://raw.githubusercontent.com/b-on-g/fragile/main/article/fragile-spread.png)

### А что с `^`

Тут смешались две вещи. `^` без имени это просто вызов родителя, `super`:

```tree
$bog_fragile_spread_keep $bog_fragile_spread_base
	sub /
		^
		<= Extra $mol_view
			sub / \Ещё
```

```js
sub(){
	return [...(super.sub()), (this.Extra())];
}
```

Он не прячет баг, а лечит «забытый `super`», это `spread/keep` выше.

А вот случайное совпадение имён с родителем существует, и `^` тут ни при чём. Это `collide/child`.

### Почему не стреляло

Выходит, что про view.tree критик прав. В ts есть слово `override`, и если его написать, переименование в родителе ловится. Во view.tree различия между «объявляю новое свойство» и «переопределяю родительское» пока нет. Я спросил об этом Дмитрия Карловского, автора `$mol`:

> Во view.tree этого пока что нет. Проблема реальна, но за 10 лет не стреляла. Да и даже в ts директива override опциональна, появилась не сразу, да и все на неё забивают.

Почему не стреляла ? Совпадение имён ловится тем, что свойства называют по смыслу. У меня в PR в piterjs на ревью попросили переименовать свойство `icon` в `upload_icon`, ровно ради этого. Случай `collide/named` в репо о том же. На практике за десять лет не стреляло ни совпадение имён, ни переименование под оверрайдом.

Есть ли смысл тогда придираться ? Кажется что нет.

<details>
<summary>Лирическое отступление про определение свойств</summary>

Мы думали сделать, чтобы отличалось, например можно новые свойства добавлять через `<= title`

```tree
$my_card $mol_view
	sub /
		<= Title $mol_view
			sub / <= title \Карточка
```

Здесь `<= title \Карточка` заводит в `$my_card` новое свойство `title`. А тут ниже только переопределение:

```tree
$my_card_news $my_card
	title \Новости
```

Если автор `$my_card` переименует `title`, компилятор скажет, что у наследника переопределять нечего. Так мы получили бы тот же `override`, что в ts, без нового спецсимвола.

Может быть, внесём это изменение, кажется, это должно упростить понимание и внести ясность в этот вопрос

</details>

### Наследовать необязательно

Забытый `super` в его классическом виде, когда наследник не вызвал инициализацию родителя, в `$mol` встречается редко: у компонентов нет жизненного цикла вроде `setup()` или `componentDidMount`, который надо не забыть вызвать. Свойство это функция от состояния, переопределил и вернул значение.

А когда компоненту нужно добавить поведение, его вообще не наследуют, а подключают сбоку. Для этого есть два механизма.

[Плагин](https://github.com/hyoo-ru/mam_mol/tree/master/plugin) это компонент без своего DOM-элемента, он работает на элементе владельца, как директива в Angular. Так подключаются горячие клавиши, жесты, навигация стрелками. Вот кусок `$mol_search`:

```tree
$mol_search $mol_pop
	plugins /$mol_plugin
		^
		<= Hotkey $mol_hotkey
			key * escape? <=> clear? null
```

Плагины родителя не теряются, их забирает `^`.

[Призрак](https://github.com/hyoo-ru/mam_mol/tree/master/ghost), `$mol_ghost`, оборачивает другой компонент и подмешивает свою логику в его DOM-элемент, не создавая лишнего узла. Так сделаны `$mol_drag` и `$mol_drop`: любой компонент становится перетаскиваемым, если передать его в `Sub`, и наследовать для этого ничего не нужно.

Про «фреймворк должен помогать совершать меньше ошибок» я согласен целиком, только посчитать стоит, где их совершить проще. В реакте есть статья с двенадцатью сценариями «нужен ли здесь useEffect», и в каждом можно выбрать не тот вариант. Я переписал все двенадцать на `$mol`: [Нужен ли здесь useEffect?](https://habr.com/ru/articles/1056766/) Выбирать там приходится из двух вариантов. Либо это действие пользователя, событие. Либо это мемоизированная ячейка, которая считается из других ячеек, и событием она быть не может. Перепутать их сложно.

### Версии

```
mobx → mobx2 → mobx3 …
```

Правда в том, что `$mol` живёт на одной ветке. Новая мажорная версия это новый модуль с новым именем, старый остаётся и может стать адаптером к новому. Патч приезжает всем сразу, при следующей сборке.

Цена подхода тоже понятна: рядом могут жить `$mol_foo` и `$mol_foo2`. За десять лет в `mol/` таких пар набралось восемь: `book` и `book2`, `object` и `object2`, `range` и `range2`, `hotkey`, `image`, `syntax`, `crypto`, а у `log` версий три.

Главное, что даёт такой подход: обновляться не страшно. Ломать совместимость внутри одного имени не принято, для ломающих изменений делаем новый модуль, а-ля `$mol_book2`, и переходим на него, когда удобно. А если кто-то всё же сломает старое имя, чаще всего это поймает компилятор, а не пользователь.

### Lock-файл

В типичном приложении на `$mol` `npm` зависимостей нет, а значит:

- нет дерева из сотен транзитивных пакетов, где версия любого может уехать;
- в собранное приложение не уезжает ни одного `npm`-пакета; ( спасибо кэп !)
- **нет возможности атаки через npm!**

Зависимости из `git` по умолчанию нигде не фиксируются. Можно зафиксировать тегом или коммитом, а штатная фиксация паков появится только с новым сборщиком, например когда мы сможем опубликовать бандл как `npm`-пакет. Поинт валидный, но далеко не такой критичный, как было озвучено.

Теперь, когда нужен `npm`. В корне `MAM` в `.npmrc` стоит `package-lock=false`, так с [марта 2019 года](https://github.com/hyoo-ru/mam/commit/c5a23c5). Когда код просит `npm`-пакет, `$node_autoinstall` зовёт `npm install <имя>` без версии, а в сгенерированный `package.json` бандла зависимость пишется как `"*"`. Повторяемой сборки в том смысле, в каком её даёт `package-lock.json`, при автоустановке нет.

Про троян. С сентября 2026 в том же `.npmrc` стоит `ignore-scripts=true`, то есть `postinstall` пакета при автоустановке не выполнится, а это основной путь, которым троян из `npm` попадает на машину.

<details>
<summary>Как зафиксировать версию npm-пакета</summary>

А версию можно зафиксировать, так делает [`yuf`](https://github.com/zerkalica/yuf/tree/master/fflate). У модуля `yuf/fflate` есть папка `.npm` с обычным `package.json`, где версия `fflate` прописана явно. Оттуда `esbuild` собирает пакет в один файл, `deploy` в `fflate.meta.tree` кладёт его рядом с бандлом, а код грузит его через `$mol_import.script`. В точку-папку сборщик `MAM` не лезет, автоустановки там нет, это обычный `npm` со всеми его инструментами, и версия в нём фиксируется как обычно. Lock-файл там тоже работает как обычно.
Выглядит и ощущается костыльно, это точно должно быть исправлено в новом сборщике.

</details>

## Модули и IDE

### FQN вместо импортов и плоский список модулей

Вот тут тоже очевидное недопонимание [`$mol` поощряет группировку по доменам](https://mol.hyoo.ru/#!section=docs/=nekayw_7ibj8f)!
и именно поэтому получаются НЕглубокие иерархии

Тысячи модулей в одну кучу никто не складывает. `$mol_button_minor` лежит в `mol/button/minor/`: домен `button`, внутри его вариации. Вложенность небольшая, потому что всё имя целиком попадает в бандл и его желательно держать коротким. А глубокое дерево папок или широкое неглубокое это шило на мыло, нужный модуль в обоих случаях находится поиском по тексту, а не прогулкой по папкам.

FQN. Импортов нет, сборщик сам строит граф зависимостей по именам, которые встретил в коде, и кладёт в бандл только их. ИМЕННО поэтому в `$mol` маленькие бандлы даже без `tree-shaking` !

Вместо того чтобы вырезать лишнее - $mol не собирает мусор. Это решение на уровне архитектуры, и в этом весь $mol, так у него во всём. Каждое техническое решение основано на техническом анализе, а не на том, что "так принято".

Критик прав, что `namespace` действительно устарел. Флаг `erasableSyntaxOnly` и запуск ts в ноде через вырезание типов неймспейсы с рантайм-кодом не поддерживают. Для `$mol` это не проблема, т.к. ts всё равно собирает сборщик, но понятно что нужно что-то думать.
В новом сборщике планируется поддержать импорты и неймспейсы.

## Итого

- **Версии.** Слабая интеграция с `npm`. Решается пока только руками: `npm` с версией и lock-файлом в папке `.npm`, свой выпуск по тегу. Штатно это закроет новый сборщик.
- **Объявление и переопределение во view.tree не различаются.** Переименование в родителе ловит только тест, совпадение имён с родителем не ловит ничего (`rename/tree` и `collide`). За десять лет это не стреляло, и от этого спасает привычка называть свойства по смыслу.

Остальное:

- оверрайды у владельца ловит компилятор, двадцать мест дадут двадцать ошибок, а не тихий развал;
- чужих пакетов в собранном приложении нет, атаковать пользователя через цепочку поставок не через что;

Синтаксис и формат ссылок это вопрос привычки, а не реальный аргумент.
